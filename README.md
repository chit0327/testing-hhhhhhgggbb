# 照樣調色（網站第一版）

上傳頁（參考圖片＋目標影片）→ 開始調色 → 調色工作區（光暗設定 → 參考導向調色 → 前後比較 → 匯出 MP4）。
**所有處理都在瀏覽器內完成**，不會上傳任何檔案。

## 安裝與啟動

需要 Node.js 18 以上，瀏覽器需要支援 WebCodecs（最新版 Chrome 或 Edge）。

```bash
cd web
npm install          # mp4-muxer、@mediapipe/tasks-vision
npm run setup        # 把瀏覽器版套件複製到 web/vendor，並下載 AI 分割模型（約 16 MB）
npm start            # http://localhost:8080/   （PORT=xxxx npm start 可以改連接埠）
```

用瀏覽器打開 `http://localhost:8080/`。WebCodecs 只能在安全環境下使用，`localhost` 符合條件；如果用區網 IP 開啟，影片匯出會無法使用。

## 操作步驟

1. **第一頁（上傳）**：參考圖片（可選）和要調色的影片或照片各有一個上傳區，可以點擊選檔或直接拖放。上傳後會顯示預覽、檔名和檔案資訊，也可以更換或移除。影片或照片載入後「開始調色」就可以按；有參考圖時網站在這時已開始分析，沒有參考圖時改用氛圍色調。
   - **第二頁（調色工作區）**：左邊約 68% 是預覽區，有三種檢視：調色預覽（代表影格，原始／調色分隔線）、處理結果影片（原片和結果並排，可以播放和同步播放）、結果分割比較（選時間點和分隔線）。右邊是調校面板，有自己的捲動，分類可以展開和收合；最下方固定放「全部歸零」和「匯出影片」。
   - 面板分成三個分頁（每次只顯示一頁，打開某個分類時會自動切到它所在的分頁）：**簡易調色**（氛圍色調、參考匹配〔含跟隨參考圖〕、快速微調（四選一）、人物膚色與背景、色溫色調與飽和度）、**效果**（局部調色及遮罩、背景模糊、柔光朦朧與暗角、匯出設定）、**專業調色**（曝光與亮度、陰影中間調與高光〔含色輪〕、色彩曲線〔含色相曲線〕、示波器）。
   - 「返回上傳」可以回到第一頁，已選的檔案和處理結果都會保留；換了檔案才需要重新處理。
   - 平板和手機（寬度 1024 px 以下）改成上下排列：預覽在上，面板在下，動作按鈕固定在畫面底部。
   - **直放（豎屏）時預覽固定在頂部**：以前整頁一起捲動，往下捲去調滑桿時預覽就離開畫面，不能邊看邊調。現在頁面本身不捲動：一行的標題列（標題、「← 返回」、狀態、深淺色）→ 預覽（固定高度，16:9 時約為寬度的 56%，最多 36% 畫面高）→ 三個檢視分頁 → 調色面板（只有這裏捲動，「簡易調色／效果／專業調色」分頁列停在面板頂部）→ 底部按鈕。預覽畫質、快速預覽、黑白檢查、參考圖收進分隔滑桿旁的「⋯」（打開時畫面高度不變）；預覽左上角「⤢」放大預覽（約 58% 畫面高），再按縮回。處理結果和分割比較的畫面自動較大。橫放和電腦版不變。實測（iPhone 390×844）：捲到「色溫」時預覽在 58–265 px、滑桿在 569 px、按鈕在 759–844 px，三者同時在畫面內；iPhone SE（375×667）和 iPad 直放（820×1180）同樣。測試：`test/e2e/mobile_layout.cjs`。
   - 進入工作區時，光暗設定視窗會自動開啟，而且同一組素材只開一次。
   - **照片**：要調色的檔案也可以是照片（JPG、PNG、WebP，依瀏覽器支援）。照片走同一套分析、光暗設定、局部調色和膚色保護，以一格影片的方式由 Worker 處理（`processPhoto`），匯出 JPEG（品質 95%），長邊最多 4096 像素。照片沒有時間軸，所以隱藏代表影格時間、同步播放和比較時間點。
   - **照片批次**：一次可以選或拖放多張照片（最多 60 張，影片仍然一次一條）。整組照片使用同一組調色設定：分析時從整組平均抽樣最多 6 張，所以 Look 代表整組；光暗設定視窗可以切換「代表照片」查看遮罩。照片只在需要時才解碼（`PhotoSet`），逐張處理、逐張壓成 JPEG，不會同時佔用大量記憶體。結果可以用「◀ ▶」逐張比較、「下載這張」單獨下載，「匯出全部照片」打包成一個 ZIP（`src/zip.js`，不壓縮，因為 JPEG 已經壓縮）。實測：30 張 3840×2160 照片約 72 秒。
   - **顯示卡（GPU）調色：第一步**（`engine/gpu.js`）：每格的調色（shaper、3D LUT 三線性插值、區域圖層如膚色保護、光暗設定的局部曝光）有了 WebGL2 版本，公式和處理器版（`render.js` 的 `renderFrame`）相同；在真實畫面和三種氛圍、兩個區域圖層、±1 檔局部曝光下逐像素比較，最大差異 1／255、平均 0（`test/e2e/gpu.cjs`）。「匯出設定 → 顯示卡測試」按鈕在這部裝置上比較兩者（720p 和 4K）；使用者的 iPad（Apple GPU）：預覽大小處理器 91 ms／顯示卡 1 ms，4K 125 ms／25 ms，差異最多 1／255。
   - **第二步：預覽和匯出使用顯示卡**（`worker.js` 的 `gradeFrame`）：第一次調色時，同一格分別用處理器和顯示卡各算一次（各先預熱一次），結果相同（差異 ≤ 2／255）而且顯示卡快 1.2 倍以上才改用顯示卡，否則留在處理器（像 AI 人物偵測的 CPU／GPU 選擇）；之後顯示卡出錯（例如瀏覽器收回顯示卡、超過 3 個區域圖層），那一格和之後都改用處理器，不中斷。處理結果資訊會寫「調色計算：顯示卡／處理器」和實測時間。（效果見第三步；背景模糊仍然用處理器。）測試（`test/e2e/gpugrade.cjs`，強制使用顯示卡比較）：預覽（含膚色保護圖層）差異最多 1／255、平均 0；匯出照片平均差異 0.000；模擬顯示卡被收回時改用處理器、畫面相同、沒有錯誤。測試環境只有軟件模擬的顯示卡，所以實測後選了處理器。
   - **第三步：效果也用顯示卡**（`engine/gpufx.js`，`worker.js` 的 `effectsFrame`）：朦朧（含背景霧更濃、霧色、柔化／發光／光幕）、柔光（含光芒顏色）、暗角、膠片的柔化／光暈／顆粒都有 WebGL2 版本，公式和次序跟處理器版（`render.js` 的 `applyEffects`、`film.js` 的 `applyFilm`）相同，每一步之間同樣存成 8 位元。每個像素的計算（縮小取平均、合成、柔化的小模糊、顆粒）在顯示卡上做；只有約 320／640 像素的小格子傳回處理器做大範圍模糊（和以前同一個函數，幾毫秒），再傳回顯示卡。選擇方式同第二步：第一格有效果時兩邊各算一次，差異 ≤ 3／255 而且快 1.2 倍以上才用顯示卡（沒有開任何效果時不測量）；出錯就改用處理器。處理結果資訊會寫「效果計算：顯示卡／處理器」；「顯示卡測試」按鈕也會比較目前設定的效果。測試（`test/e2e/gpufx.cjs`）：9 種效果組合在 1280×720 逐像素比較，最大差異 1–2／255，4K 全部效果一起最大 3／255、平均 0.014；`test/e2e/gpugrade.cjs` 在真實預覽和匯出照片中強制使用顯示卡（含效果）比較，結果相同。處理器版的效果在本機 1280×720 一格約 0.3–0.6 秒、4K 約 2–5 秒，是調色本身的數十倍，所以這一步在真實裝置上的加速最明顯；本機只有軟件模擬的顯示卡，無法量到真實速度，要用 iPad 上的「顯示卡測試」按鈕看。
   - **播放預覽**（調色預覽下方的「▶ 播放」）：影片在預覽中播放，每一格都用目前的設定（調色和效果）即時處理，調整滑桿時正在播放的畫面跟着改變，不用只對着一格調；原始／調色分割線照常可用。上一格處理完才取下一格（中間的格跳過，畫面跟得上影片），最多 640 像素寬；設定需要 AI 人物偵測時（膚色保護、AI 區域）每格都會偵測；畫在代表影格上的背景模糊選區只屬於那一格。預覽下方的時間軸顯示播放到哪裏，可以拖動：播放中拖動就從那裏繼續播；暫停時拖動會調色並顯示那一格，之後拉滑桿也是更新那一格。按「❚❚ 暫停」停在當時那一格；按「代表影格」回到調色和畫遮罩用的那一格（完整品質）；選背景模糊的筆刷等工具時也會自動回到代表影格。開啟光暗設定、匯出、離開工作區時自動停止。照片沒有這個按鈕。測試（`test/e2e/play.cjs`）：播放時顯示不同時間的調色畫面、播放中把曝光調到 −1.5 畫面立即變暗、開啟朦朧畫面立即變亮、時間軸跟着播放、播放中拖到 4.5 秒就從那裏繼續、暫停後停在當時的畫面、暫停時拖到 1 秒顯示那一格而且調曝光會更新那一格、按「代表影格」回到代表影格。本機用處理器約每秒 1 格；在用顯示卡的裝置上會快很多（速度顯示在預覽下方）。
   - **色散（RGB 分離）**（「效果」分類，`engine/fringe.js`）：像鏡頭的色差，紅色向外、藍色向內沿着由畫面中心出發的方向移開，在邊緣出現紅／青色的分離，越近四周越明顯（強度 100 時畫面角落約為長邊的 0.4%，1280 寬約 5 像素）。「只在失焦處」（預設 100）只加在對焦以外的地方：每一格（約 320 像素的格子）比較細節（每個像素和相隔 1 像素（640 寬時）／2 像素（1280 寬時）的四個鄰居的明度差）和中等尺度的明暗變化；清楚的地方兩者都有，失焦的地方只剩中等尺度的變化。先減去畫面的雜訊底線（最安靜的 10% 格子，影片顆粒和壓縮雜訊看起來也像細節），再和這個畫面本身最清楚的部分比較；沒有細節的平坦地方沿用附近的判斷（反正沒有邊緣，移色也看不見）。0 時整個畫面都有，像普通鏡頭。在調色之後、其他效果之前（它是鏡頭的效果）；也有顯示卡版本（同一套格子和公式，逐像素比較最大差異 1／255）。測試：`test/unit/fringe.test.js`（模糊的一半有色散、清楚的一半幾乎沒有、綠色不變），`test/e2e/fringe.cjs`（真實畫面：前景失焦的布保留約八成色散、清楚的樹只剩約兩成；匯出照片的設定說明有「色散」）。
   - **對焦（景深）**（「效果」分類，`engine/dof.js`、`depth.js`、`depthworker.js`）：像大光圈鏡頭的淺景深。按「選對焦點」再在預覽上點一下：每一點的模糊程度和它跟對焦距離的深度差成正比，比對焦點遠或近都會逐漸變模糊（不是「清楚／模糊」兩層）。深度來自 AI 深度模型 Depth Anything V2 Small（Apache-2.0，8 位元量化 ONNX，約 27 MB，`npm run setup` 下載到 `vendor/models`），用 ONNX Runtime Web 在獨立的執行緒計算，輸入長邊 364 像素；第一次使用時才載入，載入時顯示進度（載入執行程式、下載模型 n / 27 MB、準備模型、測試顯示卡），每一步都有時限，不會無限等待（第一版在 iPad 上卡在「載入 AI 深度模型」）。Safari／iPad 只用處理器版本的執行程式（約 15 MB，不嘗試 WebGPU）；下載的是壓縮版（`.gz`，由網頁自己解壓；執行程式 15 → 3.8 MB，模型 27 → 21.6 MB，iPad 第一次合共約 25 MB，原本約 42 MB），下載後存進瀏覽器的 Cache Storage（`zhaoyang-depth-v1`），之後再開網站直接讀取、不再下載（靜態網站的 HTTP 快取很短，Safari 也會丟掉大檔案）；大檔案在伺服器支援位元組範圍時分 4 段同時下載（延遲高的網絡上單一連線遠低於線路速度；`scripts/serve.mjs` 也支援範圍，和靜態網站一樣），下載時顯示速度，完成後彈窗寫出每個檔案的大小、秒數和速度（「慢在哪一步」）。**打開網站時就詢問**：彈窗「下載 AI 深度模型」（允許下載／稍後），允許後在背景下載並顯示進度，完成後自動關閉，也可以按「在背景繼續下載」先關掉；只下載和儲存，不把模型載入記憶體（用到時才載入，iPad 不會因此變慢）；已經存好的不再詢問，按「稍後」本次瀏覽不再詢問；下載中如果開始使用對焦，會等這次下載完成，不會下載兩次。自動化瀏覽器（測試）不詢問，除非 localStorage `zhaoyang-depth-prompt` = `ask`（`test/e2e/depthprompt.cjs`）；其他瀏覽器有 WebGPU 時，第一格分別用顯示卡和處理器各算一次，深度圖相同（平均差 < 0.02）而且快 1.2 倍以上才用顯示卡。點在人物上時（AI 人物偵測），焦點跟着**點選的那一個人**（人物遮罩按相連區域分成各個人；以前把畫面上所有人當成一個整體取中間深度，前景有一個較大、較近的人時，點選的較遠那個人反而變模糊；影片中以上一格那個人的位置找回他，所以焦點跟着同一個人），而且是點選的那個高度（點在臉上就對焦在臉，不是整個人的平均——下半身離鏡頭較近）；點在其他地方就對焦在那一點的深度，而且有**焦點範圍**（預設 35）：只有點選位置附近清楚，畫面上離它越遠就當作離對焦距離越遠（最多深度範圍的 0.35），所以點在背景一角時，同一距離的整面牆或整排建築不會全部清楚（以前會，令前面模糊的人物顯得突兀）；100 = 同一距離全部清楚，像真實鏡頭。點在人物上時不用（焦點跟着人物）。實作：把畫面距離加到深度上，再用同一套分層景深繪製（光斑和前後遮擋都照常）；深度層會覆蓋推出去後的範圍（第一版推到 0 以下的點沒有任何一層接收，保留了清楚的原像素）。繪製方法是分層景深：按深度分 10 層（其中一層剛好在對焦深度，對焦的地方完全不模糊），每層用圓形光圈模糊（大的模糊在較粗的格子上做），由遠到近疊上去，所以模糊的前景會蓋過清楚的主體，清楚的主體也不會滲進後面模糊的背景；模糊不到 1 像素的地方保留原本的像素。影片中每格都計算深度，深度範圍和對焦深度隨時間平滑，避免焦點跳動。在背景模糊之後、其他效果之前（色散「只在失焦處」會把這些新模糊的地方也當作失焦）。**光斑**（光斑亮度、光斑範圍，預設 50）：像背景模糊的散景，比四周亮得多的小光點（燈、反光）在模糊前先加亮（50 時約 16 倍），模糊後成為明亮的圓形光斑，再柔和地壓回不會過曝；大片的亮面（白牆、白桌、陽光下的地面）不算光點、不會變亮（第一版把它們也加亮，畫面發白）；加亮程度隨該層的模糊增加，清楚的地方不受影響。之前開了景深再加背景模糊的散景時，光斑「沒有出來」：背景模糊先做、景深再把整個背景模糊一次，散景的光點被糊開；現在景深自己有光斑，兩者同時開着時「對焦（景深）」下方會提醒會疊加。清楚的前景和模糊的背景之間曾經出現鋸齒狀的邊（白桌邊緣對着模糊的地板）：AI 深度圖比畫面粗約 3–4 倍，斜邊的深度一格一格地成階梯。現在深度先沿畫面本身的邊緣用導向濾波（guided filter，以明度為導引，半徑約兩格深度）細化，邊緣變成平滑的曲線；半徑再大會把桌上的影子印進深度，所以用兩格。播放預覽和時間軸上的畫面也會逐格計算深度。**模糊處噪點**（預設 50）：真實鏡頭是光線先被模糊、再落到感光元件上，所以模糊的地方和清楚的地方一樣有感光元件的噪點；把拍好的畫面模糊會連噪點也抹掉，模糊的部分顯得過份平滑（像塑膠、有色階），跟有顆粒的清楚主體不協調。現在先量度這一格本身的噪點（每點減去上下左右平均，取平坦處的第 25 百分位換算成 σ，最少 0.8），在模糊取代原像素的地方加回同樣程度的新噪點（50 = 原片的程度，100 = 19%），上下越遠越模糊（每離開一個畫面高度，深度差 1.5），「角度」±45°（正數向右上斜），像移軸鏡頭拍出的「微縮模型」效果。用同一套分層景深繪製（光斑、模糊處噪點照常），深度是按位置算出來的，不需要 AI 深度模型，也不用下載。限制：細髮絲常被當作背景一起模糊；本機（沒有顯示卡）每格深度約 0.9 秒、景深繪製約 0.65 秒（1280    - **依深度分層匹配**（「參考匹配」分類，`engine/layermatch.js`）：整體調色用整張參考圖的顏色，所以參考圖「遠處較亮、較朦朧，近處較暗」這種分層的關係會被平均掉。打開後用 AI 深度（同一個深度模型）把背景分成近景和遠景（以該畫面背景本身的深度範圍分，第 10 至 90 百分位，中間柔和過渡），各自往參考圖同一層靠近：亮度（平均明度，最多 ±0.12）、對比（明度的分佈，朦朧的遠景較平，×0.6～1.3）、色調（顏色較淡那一半的色偏，不受彩色物件影響，最多 ±0.03）和鮮艷程度（每個顏色離該層主色調有多遠，按百分位做成曲線對應到參考圖：接近灰色的幾乎不動，紅色單車、紫色招牌這類突出的顏色壓得最多；超過參考圖最鮮艷的程度再進一步壓縮；最多只加到 ×1.2，加色比減色更危險）——第一版只對應平均濃淡（×0.96），之後改對應最鮮艷的一成（×0.80），背景仍然比參考圖鮮艷：調色後灰色也帶着同一個色偏，用原始彩度分不出灰牆和紅單車；任何一層在其中一張圖少於 5% 就不調。人物（AI 人物偵測）不參與也不受影響，保持整體調色和膚色保護——只用深度時，參考圖人物的黑外套令影片裏的人也變暗（衣服是內容，不是調色）。擬合用代表影格先套用目前的整體調色再量度；強度滑桿預設 80%。影片每格都計算深度和人物遮罩，深度範圍隨時間平滑。實測（使用者的街拍影片 + 參考圖）：遠景亮 +11、對比 ×0.66、鮮艷處 ×0.83（紅、藍單車和紫色招牌明顯變淡），近景暗 −4，人物不變。測試：`test/unit/layermatch.test.js`、`test/e2e/layermatch.cjs`。結果資訊的深度一行改為「AI 深度計算」（對焦和分層匹配共用）。另外按亮度分五段量度色彩濃度（朦朧的遠景亮部近乎灰色），各段各自對應（×0.3～1.2）。量度顯示調整後背景的平均飽和度已和參考圖相若（遠景 0.099 對 0.101），但看起來仍較鮮艷：影片背景有清楚的彩色物件（單車、招牌），參考圖的背景是失焦的建築和天空。所以加了手動的**背景飽和度**滑桿（−100～+50，只影響背景，人物不變），在自動匹配之上再調；配合「對焦（景深）」把背景變模糊會更接近。**自動建議**：參考圖自動匹配完成後，在背景計算分層匹配；只有參考圖和影片的背景分層明顯不同（亮度差 ≥ 0.04、對比或鮮艷處相差 ≥ 20%）時，顯示「建議開啟」按鈕（自動匹配的說明也會提一句），按一下才套用。它不會自己開啟：開啟後匯出每格都要計算深度和人物（本機匯出慢約 40%），而且畫面在出現幾秒後自己改變，會和匯出互相干擾（試過自動開啟的版本，多個測試因此失敗）。每個參考圖和代表影格只建議一次；使用者自己勾選或取消後不再建議；換新參考圖時重新判斷。
   - **同類別匹配**（「參考匹配」分類，`engine/classes.js` ＋ `layermatch.js`）：背景分成天空、植物和建築地面（牆、路面、物件），各自往參考圖裏同一類靠近（亮度、對比、色調、鮮艷程度，量度和限制與分層匹配相同），影片的天空對照參考圖的天空、樹對照樹、牆對照牆；人物不參與。分類不用額外的 AI 模型，由畫面本身在約 96 格寬的網格上判斷：**天空**＝AI 深度最遠的一端（深度模型把天空放在無限遠）、不暗、並經由這樣的格子連到畫面頂部（雲在天空內也算）；只看亮度和平滑度時，睡房的白牆和街景的磚牆被當成天空、參考圖灰青色的多雲天空被當成植物，所以改用深度；沒有深度時只接受頂部平滑、偏藍或近白的區域。**植物**＝綠色色相（OKLab 85–178°，被調成青綠色的城市建築在 190° 以上，不算）、有一定彩度和紋理。其餘為建築地面。邊緣柔和，影片中逐格分類並和前一格平均（不閃爍）。擬合用代表影格按預覽完全相同的方式調色後量度（只用調色表時漏了膚色保護和局部層，擬合對的是另一張畫面）。顏色超出螢幕可顯示範圍時只減少彩度、保持明度（分層匹配也一樣）。明顯比同類大部分顏色鮮艷的東西（招牌、單車、衣物）是內容，保留原本的濃淡：從該類較鮮艷的四分之一開始逐步保留，而且任何顏色最多只減少 30%（第一版令樹林裏的綠色告示牌變成灰橄欖色：牌子約一半算作建築地面，而參考圖的建築地面——海邊地面——幾乎沒有顏色；修正後牌子色相不變 181°，HSV 飽和度 0.51 → 0.40，主要因為整體變亮，原本是 0.27 左右；建築地面和天空的匹配數字不變）。和分層匹配一樣**只建議、不自動開啟**；只有天空或植物兩張圖都有而且明顯不同時才建議（只有建築地面相同時，效果接近整體調色；第一版 11 組測試中 10 組都建議）。

   - **再按一下取消氛圍**：已選的氛圍卡再按一下，會取消它，回到套用第一個氛圍之前的調色（包括原本選的參考候選）；中間換過幾個氛圍也一樣。測試：`test/e2e/moodtoggle.cjs`（5/5）。
   - **換氛圍或取消時保留你自己的調整**：換氛圍或取消只換掉氛圍本身設定的部分。你自己加的效果和其他非顏色設定（暗角、顆粒、朦朧、背景模糊、對焦、人物亮度、膚色等）會保留；上一個氛圍帶來的效果（例如「夢幻朦朧」的朦朧）不會留到下一個氛圍；你在氛圍上微調的顏色滑桿按差值帶到新氛圍（例如在 A 把曝光加 0.3，換到 B 就是 B 的曝光再加 0.3）；三色調色的色相和專業調色有改過也保留。取消時回到套用氛圍前的調色，同樣保留你的效果和微調。由參考圖的調色換到氛圍時，顏色仍然由氛圍取代（氛圍本來就是取代參考圖的調色），效果保留。測試：`test/e2e/moodtoggle.cjs`（8/8）。
   - **先自動校正明暗和白平衡**（「氛圍色調」最上面的勾選，預設開；記住在這部裝置）：氛圍本身是固定的調色數值，所以以前較暗或偏色的片套上去仍然偏暗、偏色。現在選氛圍時先量度代表影格（`engine/autonorm.js`），做一個溫和的、只做一部分的校正，再套氛圍：(1) 明暗：把中位亮度往一般照片的亮度（OKLab L 0.56）移 60%，用亮度的冪曲線（黑和白不動、不會過曝），在線性光以同一倍數乘三個色版（色相和飽和度不變）；壓暗只移一半、最多 g 1.3、而且不動暗部（白色桌面、明亮房間本來就應該亮）。(2) 白平衡：取低彩度、中等亮度的表面（牆、路面、衣服、雲）的顏色當作光的顏色，以線性光的色版增益去掉其中 60%（最多算 0.03 的偏色：再大的多數是場景本身的顏色，例如橙色泥路），所以黃昏的暖光仍然保留。校正數值存在 look 裏（`autoFix`），預覽、小圖和匯出用同一組；批量照片逐張量度；整體調色強度 0% 仍是原片。設定檔只記「有開」，載入到另一段片時重新量度。量度（`test/` 外的評估：使用者的 7 段片各 2 格，加 8 張測試畫面，共 22 張未調色的畫面，17 種氛圍）：同一氛圍在不同畫面的中位亮度分散（標準差）平均 0.132 → 0.085（−36%），中性表面色偏分散 0.0142 → 0.0128（−10%）；沒有增加死黑（最多 10.9% → 4.2%）或過曝（最多 47.1% → 5.8%，白色桌面不再爆白）。例子：「黃金時刻」套在陽光下的泥路（C004）以前變成焦橙色，現在保持自然的暖色；逆光樹林（C059）暗部提亮。測試：`test/unit/autonorm.test.js`（4 項）、`test/e2e/moodautofix.cjs`（8/8：預設開、量度結果、說明文字、取消後即時跟隨、比只套氛圍更亮和更少偏黃、設定檔只記「有開」、批量照片的亮度更接近）。限制：只量度代表影格，同一段片內光線變化很大時（例如由室內走到室外）只按代表影格校正。

     - 每種氛圍就是面板上看得到的參數（曝光、對比、高光、陰影、飽和、色溫、色調、黑白位、分區色調、柔光、暗角），部分加上色相曲線（例如青橙電影把綠色推向青色）。選了以後滑桿會跟着變，可以再微調。定義在 `src/engine/moods.js`，不需要參考圖模型（`source: 'mood'`）。
     - 有參考圖時也可以選氛圍，它會取代參考圖的調色；「恢復自動匹配」可以回到參考圖。沒有參考圖時，「參考匹配」分類會隱藏（它需要參考圖）。
   - **朦朧夢幻**（「柔光、朦朧與暗角」分類）：像陽光下加了柔焦濾鏡的夢幻光感（第二版，按使用者提供的逆光人像例子重做）。三部分：(1) 細節稍微柔化（往模糊版本靠 30%）；(2) 亮部向外發光：亮部的模糊光以「濾色」疊到比它暗的周圍（白裙子的光溢到水面、陽光照到的地面溢到陰影），亮對亮不疊加；(3) 光幕：把畫面亮部的光、按它本身的顏色，均勻散到整個畫面，所以陽光場景的暗部是被暖光提亮，不是被灰霧蓋住（第一版的問題：整個畫面像蓋了一層灰綠色的霧）。已經很亮的畫面（白牆、白桌）發光會按比例減弱，避免整張變白。三部分可以用「柔化」「發光」「光幕」三條滑桿分開調（各 0–100，預設 50 = 上述的標準比例，0 = 關掉該部分，100 = 加倍）。「朦朧範圍」控制光暈多闊。朦朧是空間效果（`render.js` 的 `applyEffects`），不在 LUT 內；預覽和匯出效果一致。「夢幻朦朧」氛圍同時加上暖桃色、淡雅的調色（低飽和、暗部偏粉橙、亮部偏奶油色）。比較圖由本機產生（`evidence/` 不入版本庫）。
   - **人物、膚色與背景**（調色後在右邊的同名分類，三條滑桿）：
     - **膚色偏向參考圖**（0–100%）：預設 0%，臉色由膚色保護保持自然（膚色線 35–70°）。往右拉，膚色逐步移向調色本身給它的顏色（未保護時的顏色），100% 等於完全不保護膚色；只改顏色，不改亮度。做法：膚色圖層（`primary.js` 的 `skinFollow`）在保護與膚色線之後，把 OKLab a、b 按比例拉回調色的結果。效果大小取決於所選調色對膚色的改變：「風格」本身溫和（例：日本街景參考圖、人像，膚色色相 68° → 72°），「照搬」模式較明顯。需要參考圖（有膚色保護時才有作用），快速預覽時要停下滑桿才出現。
     - **自動判斷**：參考圖整張畫面都是同一種強烈顏色、而且幾乎沒有暖色（例如藍調時刻：平均顏色 0.09–0.13，暖色像素 < 5%）時，代表畫面裏的人也應該被這種光染色，「膚色偏向參考圖」會自動設為最多 85%（`autofit.js` 的 `autoSkinFollow`）；一般風格（膠片、青橙、綠色森林、日本街景等）保持 0%。使用者動過這條滑桿之後就以使用者的設定為準。實測：藍調時刻參考圖，人臉色相由 125°（暖）變成 228°（偏藍，和場景一致）；其他 5 張參考圖都是 0。
     - **膚色冷暖／膚色色調**（各 −100 至 100，預設 0）：膚色保護會把臉色保持在自然膚色範圍（OKLab 色相 35°–70°），所以用色溫、色輪等調整時臉色幾乎不變；這兩條滑桿專門調皮膚本身的顏色：冷暖改變皮膚的暖度（+100：b +0.03，偏橙黃；−100：較冷、較白淨），色調把膚色轉向粉紅（−）或黃（+），最多 ±15°。只改 AI 偵測到的皮膚，在膚色保護之後才套用，不會被抵消；背景不變。實測（`test/e2e/people.cjs`）：冷暖 −100／0／+100 皮膚 b 0.037／0.064／0.092；色調 −100／0／+100 皮膚色相 55°／69°／83°。
     - **人物亮度／背景亮度**（各 ±2 檔）：用每格畫面的 AI 人物／背景遮罩（和光暗設定的 AI 區域同一套：邊緣貼合、時間平滑，人物移動時跟着走），在 LUT 之後的線性光中調整曝光，可和光暗設定的區域一起使用（疊加後限制在 ±3 檔）。不放進 LUT，所以拉動時不用重新烘焙。畫面中沒有人物、或 AI 辨識失敗時沒有效果。
     - 實測（`test/e2e/people.cjs`，人像 + 日本街景參考圖）：人物 +1 檔 → 人物亮度 ×1.78、背景不變（<1%）；背景 −1 檔 → 背景 ×0.51、人物 −2%；膚色 0% → 50% → 100% 與未保護調色的距離 0.0054 → 0.0027 → 0.0000；處理後的照片和預覽一致。
   - **跟隨參考圖程度**（「參考匹配」分類，預設 0%）：「風格」為了穩定，會縮小它分不出是「調色」還是「參考圖場景本身的光線」的明暗和冷暖（一張陽光照着的照片偏暖，可能只是光線）——平均而言這樣比較準（242 例基準測試證實），但強烈風格的參考圖會「不夠像」。這條滑桿讓使用者決定：往右拉，候選的明暗曲線逐步移向參考圖的完整明暗，畫面裏接近中性的顏色（每個亮度區顏色最淡的 20%）逐步帶上參考圖在同一亮度區的實際平均顏色（用平均而非中位數：溫馨感的金黃色可能只佔畫面四分之一，中位數會忽略；參考圖裏飽和的藍色不計入，和下面一致）。顏色用「分區染色」加上（`primary.js` 的 `tint`：暗部／中間調／亮部各一個 OKLab 色偏，**避開藍色**——天空、藍色物件保持原色，灰色和暖色才染上。「避開」是漸進的：過渡寬度跟染色強度成正比（≥ 0.77 × 色偏），因為太窄的過渡會把壓縮影片在淡藍灰牆上本來看不見的 16 px 色塊（一格偏藍一點、隔壁偏灰一點）放大成一格染色、一格沒染色的粉紅／灰色格子；顏色差異最多放大約 2.5 倍，以前約 6 倍），六個數值用最小平方法一起解（`autofit.js` 的 `withFollow`）。之前試過推色輪和白平衡：暖色夠了，但天空也被染成灰綠色（天空彩度 0.031 → 0.009）。0% 時完全等於原本的候選，自動候選本身不變。實測（使用者第一章參考圖：暗部偏青、亮部暖金；平面素材）：100% 時中位亮度 0.50 → 0.42，中間調 b +0.012 → +0.027（參考圖 +0.030），金黃／橙色像素 0.3% → 18%（參考圖 25%），彩度 0.022 → 0.032（0.031），天空保持藍色（彩度 0.031 → 0.026，色相 253° 不變）；dog + coffee 參考圖：和參考圖的色差 13.5 → 12.7（50%）→ 11.9（100%）。測試：`test/e2e/follow.cjs`。

     - 明暗：原片（經過候選前段的色輪等之後）的亮度分佈對應到**整張**參考圖的亮度分佈；5 個曲線點用最小平方法配合全部 33 個分位數，而不是在固定點讀取（原片中間調擠在窄範圍時，讀取會把附近一起提得太亮：參考圖中位 0.65 做成 0.75）。拉高時允許曲線在亮部更平（斜率下限 0.45 → 0.2），陽光照到的地方不會被推成白色。以前相對「一般照片」對應，原片暗部比一般照片深時 100% 也保留深黑（霧黑 0.40 只做到 0.26），而且參考圖只看中央，中央是亮天空時會判斷得太亮。

   - **快速微調（四選一）**（「參考匹配」之後的分類）：並排顯示目前調色的四個變化——更暖、更冷、更暗更有氣氛、更像參考圖（沒有參考圖時是更亮更清爽）。選一張就套用，再在它的基礎上給四個更細微的選擇（每輪步幅 ×0.6），像驗眼「一號還是二號」，兩三輪就收斂；滑桿會同步，之後仍可微調。「重新開始」回到大步幅。拉其他滑桿時四張小圖不再每次重算（以前每次微調都清空再算四次，小圖不停改變，也增加負擔）：小圖變淡並出現「滑桿已改動：按此按目前設定更新四個選擇」，按下才重算，四張算好後一起換上。測試：`test/e2e/pick.cjs`。

     - 霧的顏色取自參考圖（勾選）：朦朧的「光幕」改用參考圖空氣的顏色（參考圖較亮的部分、排除很鮮豔的顏色後的平均色，`render.js` 的 `refAirRGB`），而不是原片本身的光色——陽光下的原片配清晨淡藍的參考圖時，以前霧是暖黃色。實測：茶色調參考圖令暗部往參考圖的空氣顏色移動。不增加處理時間。之後改為霧加上的**所有**光（包括「發光」，不只光幕）都用空氣的顏色、亮度不變：只改光幕時效果太小（樹林片段＋淡青藍參考圖，朦朧 60，畫面平均色調 b 只移動 0.003；同強度的光芒色輪是 0.024），改後移動 0.008（參考圖的空氣本身是很淡的青藍，所以仍比色輪小）；顯示卡版本同步修改，和處理器版本最多差 1／255。
     - **作用範圍**（全部／只前景（人物）／只背景）：用 AI 人物偵測把霧只加在人物或只加在背景，邊緣柔和過渡，影片中跟着人物（和背景霧更濃共用同一張經時間平滑的人物遮罩）；選「只前景」或「只背景」時「背景霧更濃」隱藏（只在「全部」有意義）；畫面中沒有人時，「只前景」沒有霧、「只背景」整個畫面有霧。實測（街景，朦朧 70，與沒有霧比較的平均提亮）：全部 人物 +6.5／背景 +8.1；只前景 +6.3／+0.8；只背景 +0.2／+7.4；顯示卡和處理器結果最多差 1／255。也會存入設定檔。測試：`test/e2e/hazewhere.cjs`。
     - 背景霧更濃（0–100）：用 AI 偵測人物，人物的霧變淡、背景的霧變濃，像遠處隔了更多空氣。只分人物和背景兩層，不是按真正的距離。實測（100）：人物被霧提亮的幅度 0.143 → 0.067，背景 0.088 → 0.104。人物遮罩直接用 AI 結果、隨時間平滑再輕微模糊（霧本來就柔和，不需要貼齊邊緣的精細遮罩：那個要每格約 38 ms）。處理時間（4 秒 720p，120 格）：朦朧 60 為 42.9 秒，加背景霧更濃為 43.4 秒（約 +1%）。需要 AI 人物偵測；用參考圖調色時膚色保護預設開啟，偵測本來就在跑。
   - **膠片質感**（「效果」分頁，`engine/film.js`）：膠片顆粒（每一格不同、按格號產生，所以預覽和每次匯出同一格都一樣；中間調最明顯）、顆粒大小、光暈（亮部邊緣滲出橙紅色光）、柔化。**膠片模板**按鈕「自動匹配參考圖」：參考圖（截圖、網上劇照）裏真正的顆粒通常已被縮放和壓縮抹去——用戶的三張膠片劇照量出來和數碼畫面一樣平滑——但膠片的明暗特徵量得到：暗部像蒙了一層霧（最暗 1% 亮度 ≈ 0.29–0.40，一般數碼 0.06–0.16）、明暗範圍窄（≈ 0.46–0.61，數碼 0.75–0.88）。所以模板按這兩項評估「膠片感」（排除黑邊），再設定顆粒、光暈和柔化；參考圖本身有明顯顆粒（例如高解析度膠片掃描）時會再加顆粒。實測：用戶三張劇照 → 顆粒 30、光暈 40、柔化 35；數碼參考圖 → 約 14–20 / 13 / 13；Portra 400 掃描（明顯顆粒）→ 顆粒較高。沒有參考圖時套用一般膠片設定。這幾項不改變顏色；霧黑和偏冷的顏色由參考圖的自動調色和「跟隨參考圖」處理。測試：`test/unit/film.test.js`、`test/e2e/film.cjs`。
   - **漸層映射**（「參考匹配」分類，預設 0%）：像畫畫先定黑白關係再上色——讀出參考圖每個亮度的平均顏色（暗 → 亮的漸層，面板上有色帶顯示），保留畫面的明暗，把顏色往同一亮度的漸層顏色拉近（`gradmap.js`，在專業調色的最後一步；膚色保護時皮膚不受影響）。實測（使用者 3 段影片 + 人像 × 6 張參考圖 = 21 組）：25% / 50% / 100% 與參考圖的色調距離 3.49 → 2.79 / 2.28 / 2.18，但同亮度物件的顏色差異只剩 82% / 66% / 51%（100% 時紅杯、綠色告示牌都變成同一種顏色）。使用者盲測 8 組：現在的「風格」3 票、25% 2 票、50% 0 票、看不出 2 組，所以不作預設，留作可選的滑桿（藍調時刻、膠片森林等強烈色調的參考圖較適合 20–30%）。
   - **參考圖小畫面**（調色預覽右上角）：有參考圖時，調色預覽的角落顯示參考圖，方便一邊調一邊對照。按一下放大／縮小，拖動可以移到別的位置（不會拖出畫面），預覽下方「參考圖」勾選框可以關掉（會記住）；畫背景模糊選取時自動隱藏，只有氛圍色調（沒有參考圖）時不顯示。測試：`test/e2e/refpip.cjs`。
   - **黑白檢查**（預覽下方）：把預覽兩邊都以黑白（感知亮度）顯示，先檢查明暗關係；只影響顯示。
   - **↺ 重設**：右邊面板每一行滑桿（包括分區色調、背景模糊、專業色輪／曲線／色相曲線）的右邊都有 ↺ 按鈕，按下把這一行的滑桿還原成預設值（曝光等回到 0、模糊強度 50、朦朧三部分 50；膚色保護在參考圖調色時回到開啟），其他行不受影響；預覽隨即更新。測試：`test/e2e/resets.cjs`。
   - **朦朧預設**（「柔光、朦朧與暗角」分類最上面）：「夢幻朦朧」（逆光人像例子：整體泛霧、暗部被光提亮）、「電影柔光」（使用者的電影截圖：黑柔焦濾鏡 Black Pro-Mist、午後陽光：亮部以較窄的光暈發光、暗部保持深沉、不加光幕、暖色光芒）、「關閉」。預設只改這一區的柔光／朦朧設定和光芒顏色，不會改任何顏色設定（測試確認）。電影柔光的數值：朦朧 45、範圍 30、柔化 30、發光 60、光幕 0、光芒 75°／35%（發光更強時亮部會在陰影裏出現一團團污跡）。原本放在氛圍色調的「電影柔光」已移到這裏（使用者要求：它是朦朧效果，不是調色）。
   - **光芒顏色**（色輪）：柔光、以及朦朧的發光和光幕加上去的光，可以染成任何顏色：拖動色輪上的點（OKLab 色相平面），方向是顏色、離中心越遠越濃，中心是畫面原本的光色；可用鍵盤 ←/→ 轉色相、↑/↓ 調濃度，↺ 還原。染色保留光的亮度（各通道係數的亮度 = 1），只改顏色（`render.js` 的 `glowTintRGB`）。
   - **背景模糊**（「背景模糊」分類）：
     - **顯示遮罩**（和「開啟模糊」分開）：選取範圍以紅色粗斜線顯示；顯示遮罩時預覽畫面暫時不模糊（只影響預覽，輸出照常），方便看清楚邊界、檢查和擦除。沒開模糊也可以先看 AI 選到哪裏。選了筆刷／橡皮擦／套索／魔術棒會自動顯示遮罩，按「開啟模糊」會自動切回顯示模糊結果；兩者都可以自己再切換。
     - 選取範圍：「AI 自動偵測背景」（每一格重新偵測，跟着人物移動）、筆刷、橡皮擦（筆刷大小：小／中／大＝畫面寬度的 2%／5%／10%）、「套索加入」和「套索移除」（在畫面上圈一個範圍）、「魔術棒加入」和「魔術棒移除」（點一下，選取和那一點顏色相近而且相連的整片範圍；比較的是和點選顏色的 OKLab 距離，亮度只算一半，所以同一面牆的光亮處和陰影處算同一片；「魔術棒容許度」預設 12，越大範圍越闊，太大會沿着相近顏色伸延到相連的物件，例如白色衣服連到淺色地面）。筆刷和套索也可以擦掉 AI 選到的部分。筆刷和橡皮擦有「筆刷大小」滑桿（1–100，半徑由畫面寬度的 0.3% 到 12%，51／76／95 約等於以前的小／中／大；最小約為 384 格遮罩的 2 格，遮罩不能更細）和「筆刷柔和度」（0 是清楚的邊；越大外圍越模糊，像噴漆一樣由中心淡出；重複塗同一處不會越塗越濃）。用手指或觸控筆塗抹時，畫面角落會出現圓形放大鏡（2.5 倍，顯示手指下面的位置、紅色遮罩斜線、十字和筆刷範圍；手指在左上方時移到右上角；放手即消失；用滑鼠時不顯示）。雙指操作（手機、iPad）：第二隻手指碰到畫面時，第一隻手指剛開始的筆畫會被撤銷（遮罩回到那一筆之前），雙指改為捏合縮放（1–6 倍）和拖動畫面，兩隻手指都放開前不會再塗到；縮放後出現「重設縮放」，離開編輯（選「不編輯」或換分頁）自動回到原來大小。縮放時筆刷在螢幕上的大小不變，所以放大後可以塗得更細（實測 2.3 倍時同一筆刷塗到的面積約為 1/11）。用手指點魔術棒時在手指離開時才選取，變成雙指就不選。「反轉遮罩」改為模糊選取範圍以外的部分。選取範圍以紅色顯示在預覽上（可關閉）。AI 只分辨「人」和「其他」，所以動物、物件也算背景。

     - 模糊效果：高斯模糊；散景 Bokeh（圓形光圈，亮點會散開成光斑；「光斑亮度」0–100 調光斑有多亮——亮點在模糊前加亮 1 + 10×亮度 倍，預設 50 即原本的 6 倍；「光斑範圍」0–100 調多亮才算亮點——線性亮度門檻由 0.8（只有最亮處）到 0.2（較暗的亮點也會散開），預設 50 即原本的 0.5；兩個預設值的結果和以前逐像素相同，`test/unit/blur.test.js`）；動態模糊（沿一個方向拉出拖影；方向 0–359°，0° 向右、90° 向上、45° 往右上，可以用滑桿，或按「在畫面上拖動設定方向」後直接在畫面上拖一下，箭頭會指向拖動的方向）。「邊界柔和度」（0–100，預設 4）控制清晰和模糊之間的過渡寬度：0 是清楚的分界，100 約為畫面寬度的 6%。三種都用「正規化卷積」：只用選取範圍內的像素計算，清晰的主體不會滲進模糊的背景，所以主體邊緣沒有光暈。在線性光下計算，約 480 px 的網格上模糊再合成回原解析度，按畫面大小計算，預覽和匯出一致。1280×720 每格約 0.2–0.35 秒（另加追蹤約 0.1 秒）。

   - **曲線編輯**：「色彩曲線」分類有可拖動的曲線圖，分亮度、紅、綠、藍四個通道，背景是代表影格的亮度分佈。調色引擎的曲線固定在 0%、25%、50%、75%、100% 五個點，所以控制點只能上下移動；曲線保持單調（不會反轉），畫出來的就是引擎實際套用的單調三次曲線。也可以用鍵盤上下鍵微調，按「重設此曲線」或雙擊恢復直線。下面的數值滑桿會同步更新。
2. 選擇光線意圖。預設是**自動匹配參考圖的光暗**：不需要選區，直接按確認即可。也可以選變亮／變暗／不同區域分別調整／保留原始光暗。
   - 在 claude.ai 開啟網頁時，會多一個選項「確認後讓 Claude 看參考圖和影格，自動再微調」。
3. 選擇區域方式：
   - **AI 辨識（預設）**：AI 提出人物、臉部與皮膚、背景等候選區域，另有亮部、暗部的亮度選區。
   - **手動選區**：在影格上用筆刷畫出範圍。
   - **整體**：調整整個畫面。
4. 按「查看」看遮罩疊色；用加筆或擦除修正；按「確認遮罩」。**未確認的遮罩不會被套用。**
5. 調整強度（預設 60%）。右邊的處理預覽是 Worker 實際算出的像素，只包含已確認的選區。
6. 按「確認並開始調色」，進入調色預覽（**這時還不會處理影片**：先在預覽上調好，避免背景處理拖慢預覽、佔用記憶體，而且一調整就要重做）。
7. 在「色彩與明暗微調」用滑桿調整，左右分隔預覽會即時顯示實際處理結果。
8. 按「匯出影片」（照片：「匯出照片」／「匯出全部照片」）。以前分開兩個按鈕（「套用並處理」和「匯出」），用戶常在處理好後想匯出時又按了一次處理，所以合併成一個：
   - 調整有改動（或還沒處理過）：彈出小視窗「顏色匹配中，請勿退出」，顯示進度條和格數，完成後自動下載並關閉視窗。iPad／iPhone 上不是由點按觸發的下載可能被擋，所以完成後視窗顯示「下載影片」按鈕，按一下才下載。
   - 結果已是目前的設定：直接下載，不會重新匹配。
   - 視窗右上角的圓形 × 按鈕（或 Esc）會問「顏色匹配中，如果現在選擇退出想要進行修改的話，需要重新匹配顏色和效果，你確定要返回調色介面嗎？」：「否」繼續匹配；「是」停止匹配、回到調色預覽，不會下載，之前處理好的結果保留。正在問的時候剛好匹配完成，會等用戶回答（「否」才下載）。
   - 「匯出設定」裏的「以目前設定重新處理」只處理不下載。測試：`test/e2e/export.cjs`。
   - **柔光與暗角**：柔光把亮部模糊後疊加回去（類似柔焦或霧鏡），可以調強度和擴散範圍；暗角正值壓暗、負值提亮四周，可以調範圍。這兩項取決於位置和周圍像素，不能放進 LUT，由同一個渲染器在 LUT 和局部曝光之後以線性光計算，預覽和匯出一致；不受整體調色強度影響。開啟後 1280 px 影片每格大約多 50 至 100 毫秒。
   - **整體調色強度**：0% 是原片，100% 是完整效果，自動匹配和 Claude 看圖都適用（在 OKLab 中混合）。光暗設定的局部曝光不受影響。切換調色來源時會保留設定值。
   - 接近參考程度：0% 只做自然轉移；越高，明暗曲線和飽和度越接近參考圖。
   - 參考色彩強度、保護材質顏色（避免草地、皮膚被染成別的顏色）。
   - 曝光、對比、高光、陰影、飽和度、色溫、色調。雙擊滑桿可以歸零。
   - **黑位提亮、白位**：做出霧面、底片感的暗部，或讓亮部不要死白。
   - **分區色調**：陰影、中間調、亮部各自選一個顏色和份量，例如亮部偏黃、暗部偏蜜桃色。
   - **自動調色候選（預設）**：素材載入後，網站從參考圖自動算出四種詮釋（推斷風格、自然、忠實、濃烈；預設用「自然」），並在代表影格上實際量測：與參考圖的 CIEDE2000 色差、結構保留、膚色變化、裁切比例。
     - 預設使用「自然」，使用者只要挑一個；三種詮釋分別是「自然」「忠實」「濃烈」。
     - 參數使用專業調色引擎：Lift / Gamma / Gain / Offset 色輪、亮度與 RGB 曲線、Hue vs Hue／Sat／Lum 色相曲線、膚色保護。
     - 想自己調整時，展開「陰影、中間調與高光」（色輪）、「色彩曲線」（曲線、色相曲線）等分類修改，或在「匯出設定」匯出 `.cube` LUT。
   - **示波器**（面板裏的「示波器」分類，`src/engine/scopes.js`）：目前結果（可改看原片）和參考圖中央 70% 並排顯示，每次預覽更新時重畫。
     - 波形圖（亮度）和 RGB 分量圖：顯示 0、25、50、75、100% 刻度。
     - 向量圖：Rec.709 Y'CbCr，標出 75% 色條目標和膚色線。
     - 下方顯示過曝（任一色版 ≥ 254）和死黑的比例。
     - 示波器只讀取 8-bit 顯示結果，和匯出的影片一致；不會顯示超出 0–100% 的數值。
   - **舊的參數式自動匹配**：只在沒有候選時作為後備。素材載入後，網站自動量化參考圖的黑白位、對比、飽和度和亮部、暗部色偏，直接填入上面的滑桿。參考色彩強度會設為 0，所有變化都會顯示在滑桿上。動過滑桿之後就不再自動覆蓋；按「恢復自動匹配」可以回到自動值。
   - **Claude 看圖自動調色**：只在 claude.ai 的網頁檢視裏出現，使用 `sample` 功能，花的是瀏覽者自己的 Claude 用量，第一次使用會先詢問。
     1. Claude 看參考圖、原始影格、目前結果和量化數據，回覆一組滑桿數值和一句說明。
     2. 最多 3 輪，Claude 認為接近時就提早結束。
     3. 回覆的數值會先限制在滑桿範圍內才套用；畫面仍由同一個 LUT 產生。
9. 比較原始和處理後的影片，可以同步播放，也可以在同一時間點拖動分隔線比較。需要時按「返回修改光暗設定」，再重新處理。
10. 結果已是目前的設定時，再按「匯出影片」會直接再下載一次，不會重新處理。

## 專業調色引擎與自動擬合（原型）

AI 只負責推斷要怎麼調，畫面一律由固定的調色引擎處理：原始畫格經過同一個 LUT，構圖、物件和紋理都保持不變，也不會把生成的圖片當成影片畫面。

- **引擎**（`src/engine/primary.js`）：
  - Lift / Gamma / Gain / Offset：每個色輪有亮度，以及以 OKLab 色相表示的顏色和份量。顏色不改變亮度，超出白色的色版會截在 1，所以 Gain 可以為白色加上色調。
  - 曲線：亮度曲線（在 OKLab 中作用，不改變色相）和 RGB 曲線，用 5 個控制點的單調三次插值。
  - 色相曲線：紅、橙、黃、綠、青、藍、紫、洋紅 8 個錨點，各自調整色相、飽和度、亮度；灰色不受影響。
  - 以上全部只取決於顏色，所以一起烘焙進 41³ LUT。LOG 還原（明暗大幅拉開）時，LUT 前面加一條 1D shaper，把格點集中在顏色變化快的亮度範圍。在使用者示意圖的 LOG 影格（「濃烈」調色）上，和精確計算相差超過 4/255 的色值比例：33³ 均勻格 33.6%，41³＋shaper 1.9%（`test/unit/lut.test.js` 的測試素材）。
  - 匯出的 `.cube` 是 65³ 均勻格，任何調色軟體都能讀。端到端測試用 ffmpeg `lut3d` 套用這個檔案，結果和網站畫面平均相差 0.52/255。不過 `.cube` 沒有 shaper，LOG 還原這類極端調色的精度較低：同一張 LOG 影格上，65³ 有 6.8% 的色值偏差超過 4/255。
- **膚色保護**：用位置判斷，不用顏色。磚牆、米色大衣和皮膚的色相相同，用顏色無法分開。處理程序在 AI 皮膚遮罩（加時間平滑）內，混入一張「只有明暗、沒有色彩變化」的 LUT。
  - 膚色線（`primary.js` 的 `SKIN_LINE`）：皮膚可以跟着調色變化，但色相限制在 OKLab 35–70°（自然膚色）。之前上限是 80°，遇到黃綠色菲林色調的參考圖（例如日系街景），皮膚會變成偏黃綠、略帶青的顏色；改為 70° 後保持暖色到橄欖色之間。
  - 「忠實」和「濃烈」的膚色保護只有 60% 和 35%，皮膚可以跟調色走得更遠，但最後一定回到膚色線內，而且至少保留原本 60% 的彩度。之前在強烈青色調下，混合後的皮膚會變成接近灰色，旁邊是青色，看起來就是青色。
  - 調色把皮膚推到完全無關的色相（超出膚色線 45° 以上，例如青色）時，皮膚保留自己原本的色相（青橙電影的做法）；只超出一點（例如偏黃綠）時，移到最近的邊界。
  - 實測（AI 皮膚遮罩內的平均色相，原本 52–62°）：日系街景參考圖在人像上由 80°／91°／101°（自然／忠實／濃烈）改為 71°／72°／73°，紅色成分由 −0.9 回到 +1.3；原本已經自然的膚色（例如杯子人像配自己的參考圖）不變。
- **風格（預設候選）與風格・濃**（`autofit.js` 的 `fitLook`）：參考圖相對「一般照片」來讀，而不是相對使用者的畫面，所以同一張參考圖套在任何畫面都得到同一種風格。明暗（亮度分位數）、色調（每個明暗段的 a/b）和 8 個色相區的顏色傾向，都和 59 張自然照片的統計比較；每個估計按「超出一般照片之間正常差異多少」加權（差異小 → 可能只是內容不同 → 少套用）。整體強度：風格 ×2、風格・濃 ×3。
  - 實測：真實風格基準（11 個菲林 LUT × 22 張照片，242 例，ΔE 越低越好）11.11（舊預設「自然」11.64、不調色 11.91）；測試圖像參考圖程度 14.2（自然 14.8）；穩定度（同一參考圖配 6 個畫面的差異）1.9（自然 9.8，約 5 倍）。使用者盲選勝自然約 5 : 3。研究紀錄：`research/look_stable/`。
  - 「照搬・自然／忠實／濃烈」保留為選項：直接搬參考圖的顏色分佈，效果較強，但會隨畫面內容變化（內容和參考圖差很遠時，例如粉紅色牆可能變橙）。
- **自動擬合**（`src/engine/autofit.js`，固定演算法，同樣的輸入一定得到同樣的結果）：
  0. **LOG／平面素材還原**（第一個節點，相當於達文西的色彩空間轉換）：只看原片本身。亮度範圍（第 1 到第 99 百分位）小於 0.6（OKLab L）就判斷為平面素材，越平還原越多。還原時以中間亮度為中心拉開對比，兩端用 tanh 柔和收尾，不會截斷；彩度提高到正常水準（最多 ×4）。正常素材的還原強度是 0。
  1. 明暗：用亮度分位數擬合亮度曲線，忽略死白的天空，並限制變化幅度和斜率。黑點和白點不超出 0 到 1，避免暗部被壓成純黑或亮部被截斷。
  2. 色彩：暗部、中間調、亮部的色偏換算成 Lift / Gamma / Gain 色輪。每一步都把樣本像素實際送進引擎，量測反應再修正；步長受到限制，結果沒有變好就把步長減半。
  3. 色相：每個色相錨點轉向參考圖附近的色相、配合它的飽和度；參考圖沒有的顏色會被降低飽和度，例如冷調參考圖下的暖色磚牆會變成灰綠。
  4. **分佈最佳化**：以上第一輪結果再逐一微調所有參數（色輪、亮度曲線、飽和度、色相曲線），讓調色後原片的色彩分佈接近參考圖。距離用 OKLab 的 sliced Wasserstein（27 個固定方向），用座標下降法，結果固定。有四道保護：
     - 與第一輪的差距有懲罰，亮度相關參數尤其嚴格。
     - 參考圖過曝的像素（天空、沙地）不計入。
     - 相對於還原後的畫面，整體亮度轉換的斜率保持在 0.45 到 2.5 之間。
     - 在一張縮圖上量結構保留，「濃烈」低於 0.95 就把最佳化逐步退回第一輪，直到達標。
  5. **自動局部調色**（`src/engine/local.js`）：全畫面調色後，按 AI 區域各自微調，再以區域遮罩混合（每個區域一張 LUT，遮罩經過時間平滑和邊緣貼合）：
     - 皮膚：調向參考圖的膚色，但限制在自然膚色範圍（OKLab 色相 25°–85°、彩度 0.03–0.12）。參考圖的臉被調成青綠色時，影片的皮膚不會跟著變綠。
     - 背景：只對準參考圖背景裏「彩度較低一半」像素的色偏（環境色調），不改變物件本身的顏色。
     - 頭髮、衣服：保持全畫面調色，不受背景調整影響。曾試過對準參考圖的衣服，結果在參考圖有深藍外套時，把米色風衣調成淡紫色，所以沒有採用。
     - 任一張圖中某區域少於 1.5% 就不調整。「自然／忠實／濃烈」分別使用 60%／100%／120% 的局部強度；專業面板可以調整局部調色強度。
     - LOG／平面素材會先還原再做 AI 分割：未還原的 LOG 畫面，人物只辨識出 11%，還原後是 31%，和調色後的版本一致。
     - 天空：AI 模型沒有天空類別。試過依亮度、平滑度、顏色和是否連到畫面頂部來判斷，結果會漏掉青綠色或有雲的天空，又會把遮陽篷和牆誤判成天空，所以沒有採用。需要有天空類別的分割模型（例如 ADE20K），這個開發環境無法下載。
     - 匯出的 `.cube` 只包含全畫面調色；自動局部調整（背景、皮膚、人物）需要遮罩，無法放進單一 LUT。
  6. 四個候選：
     - 「忠實」是最佳化結果，「自然」和「濃烈」是同一組調色的 65% 和 125% 強度，各有不同的膚色保護。這三個都是**直接匹配**參考圖的顏色。
     - **「推斷風格」**：不拿影片和參考圖互相比對，而是把參考圖當成「一般照片套上某個 look」，和 59 張一般未調色照片的統計比較，推算出 look 本身：明暗曲線取一半強度，中性色色偏取參考圖各亮度區彩度最低 5% 的像素。不估計飽和度和色相，因為這兩項在測試中都會變差。
     - 限制：參考圖某個亮度區如果完全沒有接近中性的像素（例如暗部全是草地），色偏仍會受內容影響。
  - **已知 look 測試**（`research/export_web_bench.py`、`research/bench_web.mjs`）：
    - 11 個第三方底片／電影 LUT，套在 22 張 FiveK 照片上，共 242 題。
    - 每題用「look 套在另一張照片」當參考圖，處理影片後和「look 套在這張照片」的真實答案比較逐像素 CIEDE2000。

    | | 不處理 | 推斷風格 | 自然 | 忠實 | 濃烈 | 四個候選挑最好 |
    |---|---|---|---|---|---|---|
    | ΔE | 11.91 | **9.99** | 11.63 | 13.65 | 15.14 | **8.17**（只有後三個是 10.70） |

    - 「推斷風格」在 242 題中有 158 題最接近答案。直接匹配在細膩的 look（Velvia、Portra、Kodachrome）上會把參考圖的內容顏色帶進來，在強烈的 look（夕陽、月光）或內容相近時才明顯較好。
    - 預設仍是「自然」：使用者偏好接近參考圖的效果，而且挑選的多是風格強烈的電影畫面。「推斷風格」在使用者的影片上效果很保守，例如冷調青綠參考圖下幾乎看不出青綠色，因為那張圖的風格主要在各顏色的色相和飽和度，不在中性色。
  - 為什麼這樣設計：用使用者提供的 LOG／Rec709／GRADE 示意圖（同一格畫面的三個版本）驗證，可以逐像素量測。

    | 從 LOG 調到 GRADE（逐像素 CIEDE2000） | 整體 | 頭髮和皮膚 |
    |---|---|---|
    | LOG 原片 | 21.6 | 17.8 |
    | 舊版「忠實」 | 9.2 | 12.3 |
    | 加入還原 | 5.8 | 10.3 |
    | 加入還原和分佈最佳化（目前版本） | **4.2** | **6.1** |
    | 上限：同一引擎直接對準 GRADE 逐像素擬合 | 4.2 | 5.5 |

## 處理流程與資料路徑

**處理速度（流水線）**：影片處理是一條流水線，各階段同時處理不同的畫格（最多 4 格同時進行）：
**AI 人物偵測用處理器（CPU）還是顯示卡（GPU）**：第一次載入模型時，網站在幾張小畫面上分別計時（包括把結果讀回來——GPU 版的呼叫只是排隊，讀回結果時才真正計算），GPU 明顯較快（≥ 1.3 倍）才用 GPU，否則用 CPU；GPU 不可用或出錯也用 CPU，所以不會在任何裝置上變慢。只在頁面上計時一次，AI 分割 worker 直接沿用結果。GPU 和 CPU 的遮罩只有浮點誤差（平均差 0.001，邊緣最多 0.14）。這個開發環境沒有真正的顯示卡（軟件模擬）：CPU 每格約 365–404 ms、GPU 約 2,000 ms，所以這裏會選 CPU；有真正顯示卡的電腦通常 GPU 快好幾倍，但未能在這裏實測。處理完成後結果資訊會顯示用了哪一個和兩者的實測時間。

1. **解碼**（主執行緒）：用 WebCodecs `VideoDecoder` 從頭到尾連續解碼（`vdecode.js`，mp4box.js 拆檔），不再每格跳轉 `<video>`（跳轉要從關鍵格重新解碼並等畫面呈現）。選格規則和跳轉完全一樣（時間 t 顯示的那一格），實測逐格比對完全相同（包括最後幾格：解碼器 flush 完才算結束）。旋轉過的手機影片、非 MP4／MOV、或瀏覽器不支援該編碼時自動改用原本的跳轉方式。處理期間只有隱藏的工作影片在解碼原片：上傳頁的影片預覽和比較頁的兩個播放器會先卸載，處理完成後再載入（iPad 上每個載着 4K 影片的 `<video>` 都佔用一個硬體解碼器和大量記憶體；處理和畫質不受影響）。iPad／iPhone／Safari（WebKit）上以前不用 WebCodecs 解碼（使用者在 iPad 上遇到「Decoder failure」），但逐格跳轉是匯出最慢的一步：實測（C197，1280×720、223 格，模擬 iPad 的跳轉方式）每格 609 ms 之中讀取影格佔 552 ms，用解碼器只要 13 ms（整段 135.8 → 50.9 秒）。現在 WebKit 也先用解碼器：第一格同時用跳轉方式讀取並比較（平均差 ≤ 8 才繼續用解碼器，否則整段改用跳轉），之後解碼器出錯或沒有回應也會改用跳轉繼續（`WEBKIT=1 LOWMEM=1 node test/e2e/pipeline.cjs`；加 `CHECKFAIL=1` 令第一格比較失敗；兩者結果都和舊方法逐格相同）。實機 iPad 未驗證，結果頁的「每格時間」會寫出用了哪一種讀取方式。其他瀏覽器如果解碼器在中途出錯，餘下的畫格自動改用跳轉方式繼續，不會中斷（`FAILAT=20 node test/e2e/pipeline.cjs`：第 20 格故意令解碼器出錯，結果和舊方法逐格相同）。
   - **記憶體**：影片檔不會整個讀進記憶體（以前整個檔案讀入一次，解碼時再複製一份所有影像樣本，手機 0.5–2 GB 的影片會令瀏覽器「out of memory」）。現在只讀檔案的索引（moov，逐 MB 讀並跳過影像資料，`mp4index.js`），影像和音訊樣本處理到哪裏才從檔案讀到哪裏（每次最多 4 MB）。每格畫面直接移交給調色 worker 而不是複製。每個 AI 分割 worker 各自載入模型（約 150 MB）。**省記憶體模式**（iPad／iPhone 上的所有瀏覽器，以及回報記憶體 ≤ 4 GB 的裝置自動使用；iPad 的分頁大約 1–1.5 GB 就會被系統停止）：AI 分割改在主執行緒用預覽時已載入的模型（不另外載入），同時處理 2 格而不是 4 格，解碼器只預先解 2 格而不是 6 格；調色結果逐格相同（`LOWMEM=1 node test/e2e/pipeline.cjs`），速度較慢。實測（90 秒 1080p、137 MB 的影片，Chromium 全部程序合計）：處理時最高 2.48 GB → 2.33 GB；20 秒片段不開分割 worker 1.96 GB、開兩個 2.27 GB。調色結果逐格相同。
2. **AI 分割**：在獨立的 worker 執行（`segworker.js`，4 核心機器開 2 個、輪流處理；最多 3 個），結果和主執行緒完全相同；worker 無法啟動時改回主執行緒。
3. **調色**（render worker）：畫格嚴格按順序送入（遮罩的時間平滑、背景模糊的追蹤都依賴順序），按順序編碼。
實測（使用者 1080p 30fps、14.6 秒、437 格、參考圖調色＋膚色保護，輸出 1280 寬）：舊方法 364–460 秒 → 新流水線 102–111 秒（約 3.6–4.1 倍）；每格：取畫格 389 → 22 ms。編碼前的調色結果和舊方法逐格完全相同（`test/e2e/pipeline.cjs`）。處理完成的記錄 `processing-done` 附有各階段耗時（`timing`），結果頁也會寫出**每格時間**：實際每格、讀取影格（解碼器／逐格跳轉，以及有沒有改用跳轉）、AI 人物偵測、AI 深度、調色引擎（再分膚色／局部層、調色、景深、效果等）、等待和編碼；AI 步驟和讀取同時進行，所以各項加起來會多於實際時間。試過「每兩格才做一次 AI 分割、中間格取平均」：只快 11%（之後瓶頸變成調色 worker），不值得冒遮罩品質的風險，沒有採用。

```
參考圖片 ─┐
           ├─ worker: fitGrade（6 張關鍵格 + 參考圖中央 70%）→ 41³ LUT＋shaper（每段影片只擬合一次）
目標影片 ─┘
對話框草稿 LightingIntent ── confirmIntent() ──► 已確認 LightingIntent（序列化、雜湊）
                                                     │  postMessage（start-job）
逐格：<video> 對齊畫格中心跳轉 → 畫格 ─► MediaPipe 分割（只在用到 AI 選區時）
        └────────────► worker.render：區域遮罩（時間平滑 + 筆刷修正 + 羽化）→ 曝光場（檔）
                        → 線性光局部曝光（亮部柔和壓縮）→ 參考 LUT → RGBA
                        → VideoEncoder（H.264）→ mp4-muxer → 預覽影片 = 匯出檔
```

- **全域調色**（`src/engine/grade.js`）：移植自研究方法 B1（OKLab 色群的非剛性點集配準，在真人盲測中表現最好、且不需要大型模型）。另外限制色相旋轉最多 30°，保護材質顏色，例如草地不會被轉成棕色。
- **色彩與明暗微調**（`gradeColour`）：接近參考程度會把明暗曲線（限制斜率並平滑，避免斷層）和飽和度水準拉向參考圖，色彩方向仍由自然轉移決定。基本調整也一起烘進同一個 LUT。
- **局部曝光**（`src/engine/render.js`、`masks.js`）：強度 100% = ±1 檔，60% = ±0.6 檔。多個區域重疊時檔數相加，上限 ±1.5 檔。提亮時亮部用柔和曲線壓縮，不會死白。順序是**先套全域 LUT，再做局部曝光**：LUT 是用沒動過的原始畫格擬合的，局部曝光在最後套用，所以設定 +0.6 檔，結果就是 +0.6 檔。
- **AI 遮罩**：先用畫面亮度做導向濾波，讓遮罩邊緣貼合真實邊緣；再做柔和門檻，內部補成 1、背景殘留歸 0。這樣可以避免提亮人物時，周圍出現一圈光暈。
- **LightingIntent**（`src/engine/intent.js`）：結構化、可序列化的狀態。草稿和已確認版本分開保存；區域有 `proposed`（候選）和 `confirmed`（已確認）兩種狀態；`effectiveRegions()` 只回傳已確認的區域；`hashIntent()` 讓 UI、Worker 和匯出可以核對雙方收到的是同一份設定。
- **單一渲染器**：對話框預覽、結果預覽和匯出都由 `src/worker.js` 的同一個 `renderFrame` 產生，頁面本身不產生任何像素。

## 已知限制（第一版）

- **瀏覽器**：在最新版 Chrome 和 Edge 上測試過（需要 WebCodecs H.264 編碼）。
  - iPad 和 iPhone 上的所有瀏覽器都是 WebKit 核心：網站會把取畫格用的影片放進頁面，每次跳轉後等畫格真正顯示才擷取，並改用一般 canvas，避免黑屏。
  - 這個 WebKit 取畫格方式只在 Chromium 裏強制測試過（`WEBKIT_MODE=1 npm run test:e2e`），還沒有在實機 iPad 上驗證。
  - 匯出影片需要瀏覽器支援 WebCodecs H.264 編碼；iPadOS 上是否可用取決於系統版本。
- **規模**：建議影片 60 秒以內，輸出最長邊 1280 px。逐格跳轉擷取畫格，速度約為即時的 0.5 倍（4 秒的 640×360 影片在測試環境約 7 秒）。
- **音訊**：匯出的影片沒有音軌。
- **AI 區域**：只有人物、臉部與皮膚、背景（MediaPipe 人像模型）。天空、牆面等語意區域沒有可在瀏覽器執行的模型，目前只能用亮度選區或手動選區代替。
- **跨影格追蹤**：
  - AI 選區每格重新分割，再做時間平滑（指數平均，α = 0.5）。
  - **筆刷修正和手動選區固定在畫面座標，不會跟著物體移動**，只適合固定鏡頭。
  - 人物區域有可量測的逐格亮度抖動（約 0.027 檔／格，背景是 0.002），見 `tools/temporal_check.py`。
- **局部曝光的實際幅度**：測試中設定 +0.6 檔，最終人物亮度約 +0.53 檔，背景只變 +0.002 檔。差距來自亮部的柔和壓縮和遮罩邊緣。
- **全域調色**：使用研究方法 B1，沒有語意限制。參考圖和影片內容差異很大時，仍可能把參考圖的顏色帶進不相干的區域；色相保護只能部分緩解。
- **接近參考程度的明暗**：
  - 分析參考圖明暗時，會排除接近純白的死白區域（天空、窗戶）。這類區域如果佔參考圖很大比例，照抄會讓沒有天空的影片大片過曝。實測一張約三分之一是白天空的參考圖：修正前會讓街景 20% 的像素接近純白，修正後只剩 0.3%。
  - 每個亮度最多提高或壓低 0.2（OKLab L），再亮就要自己拉曝光。
- **接近參考程度**：只控制明暗曲線和飽和度水準。直接平移色偏、或依亮度分區平移色偏的做法都試過，在內容差異大時會造成紫色陰影、色塊或漏掉暖調，所以沒有採用。
- **膚色**：以 AI 皮膚遮罩做保護和局部調色；遮罩只來自 MediaPipe 人像模型，側臉、很小的臉或戴口罩時可能漏掉。
